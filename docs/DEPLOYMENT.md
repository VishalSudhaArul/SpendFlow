# Deployment

SpendFlow AI is deployed as two pieces:

| Piece | Host | Config in repo |
|---|---|---|
| React client (static) | Vercel | `client/vercel.json` |
| Express API | Render (web service) | `render.yaml` |
| Database | MongoDB Atlas | — |

Vercel serves the app and **proxies `/api/*` to Render**. To the browser, the app and the API share one origin, so the session cookie is first-party (`SameSite=Lax`), CORS preflights disappear, and nothing needs `SameSite=None`.

```
https://<app>.vercel.app/            → static React build
https://<app>.vercel.app/api/...     → rewrite → https://<api>.onrender.com/api/...
```

Secrets are entered only in the Render dashboard. Nothing secret is ever set on Vercel, because the client needs no secrets.

---

## 1. MongoDB Atlas

1. Use your existing cluster or create a free M0 cluster.
2. **Database Access:** create a database user that has *readWrite* access only to the `spendflow-ai` database.
3. **Network Access:** Render's free plan has no fixed outbound IP, so the access list has to allow `0.0.0.0/0`. The database is then protected only by the user's password, so use a long random one. On a paid Render plan, you can restrict the list to Render's published outbound IP ranges for your region instead.
4. Copy the connection string (Connect → Drivers). You'll paste it into Render in step 2, nowhere else.

## 2. API on Render

1. Push the repository to GitHub.
2. In Render, choose **New → Blueprint**, then select the repository. Render reads `render.yaml` and proposes the `spendflow-ai-api` web service.
3. Render asks for the variables marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `MONGODB_URI` | your Atlas connection string |
   | `GEMINI_API_KEY` | your key from Google AI Studio (leave empty to use the fallbacks) |
   | `CLIENT_URL` | the Vercel URL from step 3, for example `https://spendflow-ai.vercel.app`. Use a placeholder for now and update it later. |

   `JWT_SECRET` is generated by Render (`generateValue: true`), so you never have to see it.
4. Deploy. When the service is live, check it:

   ```powershell
   Invoke-RestMethod https://spendflow-ai-api.onrender.com/api/health
   ```

   You should see `status: ok`. In production the health route reports nothing beyond status and time.

> If Render gives the service a different URL (for example because the name is taken), note it down for the next step.

## 3. Client on Vercel

1. If your Render URL differs from `https://spendflow-ai-api.onrender.com`, edit the first rewrite's `destination` in `client/vercel.json` and commit the change.
2. In Vercel, choose **Add New → Project**, import the repository, and set **Root Directory** to `client`. Vercel detects Vite, and `vercel.json` supplies the build command and output folder.
3. Leave `VITE_API_URL` unset. Production builds default to `/api`, which goes through the proxy.
4. Deploy, then copy the production URL into Render's `CLIENT_URL` (step 2). Render redeploys automatically.

`vercel.json` also adds:

- An SPA fallback, so deep links like `/budgets` load the app.
- Long-term caching for hashed `/assets/*` files.
- Security headers: a strict Content-Security-Policy, HSTS, `X-Frame-Options: DENY`, `nosniff`, a referrer policy and a permissions policy.

The CSP allows the one inline script in `index.html` (the theme loader that prevents a light/dark flash) by its SHA-256 hash. If you edit that script, `npm run build` fails and prints the new hash to put in `vercel.json`.

## 4. Proxy hops (`TRUST_PROXY`)

Rate limiting keys on the client's IP address, which Express reads from `X-Forwarded-For`, trusting the number of proxies set in `TRUST_PROXY`:

- Vercel → Render (this setup): `2` (already set in `render.yaml`)
- Calling Render directly, with no Vercel proxy: `1`

If the value is too low, every visitor appears to share the proxy's IP and rate limits are shared. If it's too high, clients can spoof their IP.

## 5. Post-deploy checklist

- [ ] `https://<app>.vercel.app/api/health` returns `ok` (this proves the proxy works).
- [ ] Register a new account, refresh the page, and confirm you are still signed in (the cookie is working).
- [ ] In DevTools → Application → Cookies, `sf_session` shows `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/api`.
- [ ] Deep-link to `/analytics` and refresh: the page loads.
- [ ] AI coach shows "Gemini connected" (or explains that fallbacks are in use).
- [ ] No CSP errors in the browser console.
- [ ] Optional: seed demo data in production with `npm run seed` from your machine, with `MONGODB_URI` pointing at the production database. It only creates or resets the demo account.

## Notes and limits

- **Cold starts:** Render's free plan sleeps after about 15 minutes idle, and the first request can take about a minute. If that request times out, the client shows an error saying the server took too long, and a retry works once the service is awake. A paid instance avoids this.
- **One instance:** rate-limit counters are in memory. If you scale to several instances, add a shared store (for example Redis).
- **Alternative (no proxy):** the API can also be called cross-site. Set `VITE_API_URL=https://<api>/api` on Vercel, `COOKIE_SAME_SITE=none` and `TRUST_PROXY=1` on Render, and remove the `/api` rewrite. Some browsers block third-party cookies, so the proxy setup is recommended.
- **Rotating secrets:** changing `JWT_SECRET` signs everyone out. Rotate the Gemini key or Atlas password in their consoles first, then update Render.
